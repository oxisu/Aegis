# 沙漏模型：代理软件管域名，Aegis 管网卡

> 本文把"沙漏 / 纵深防御"这套想法落成**可执行的工程语言**，
> 并写清**哪些已经实测成立、哪些还只是想法、哪些还没做**。
>
> 一句话：**Aegis 不需要懂域名，它只需要当好那个"物理保安"——
> 看每一跳从哪张网卡出去，走错了就砍。**

---

## 1. 两层漏斗各管什么

```text
        应用发起连接（目的 = 真实域名/IP）
                  │
    ┌─────────────▼──────────────┐
    │ 第一层（上）：代理软件       │  用户态，懂 HTTP/HTTPS，看得到域名
    │ Clash / sing-box / HypoMux  │  按规则决定：直连 / 走隧道 / 拒绝
    └─────────────┬──────────────┘
                  │ 封装进代理隧道（TUN 虚拟网卡）
    ┌─────────────▼──────────────┐
    │ 第二层（下）：Aegis（WFP）  │  内核态，**不懂也不需要懂**域名
    │ 只判一件事：                │  这一跳是不是从**该走的网卡**出去？
    └─────────────┬──────────────┘
                  │
              物理网卡 → 外网
```

两层各自只做自己擅长的事：

| | 第一层（代理软件） | 第二层（Aegis） |
|---|---|---|
| 看得见 | 域名、SNI、HTTP 头 | 网卡、端口、进程映像路径、地址 |
| 看不见 | 物理网卡身份 | **域名**（已实测，见 §2） |
| 判据 | "这个域名该不该走代理" | "这一跳走没走对网卡" |
| 失效时 | 漏到第二层 | 直接断（fail-closed） |

**关键点：两层的判据不重叠，但覆盖互补。** 第一层漏掉的（比如流氓软件
绕过代理直连、代理进程崩了没接住），第二层不看它是哪个软件，只看它有没有
走对网卡 —— 走错就砍。这就是纵深防御。

## 2. 第二层为什么不能做域名（已实测）

`examples/name_probe` 第二幕：把 `www.baidu.com` 以 UTF-16LE + NUL 塞进
`FWPM_CONDITION_ALE_EFFECTIVE_NAME` 的 blob，装一条 Block，**装住不拆**再测：

```text
✅ 内核接受了（id=[…]）—— 只说明参数合法
   直连 183.2.172.177:443   通   ← 没拦住
```

**装得上 ≠ 拦得住。** 所以 `Condition::RemoteName` 被刻意排除在可映射白名单
外（`preflight` 会拒绝含它的计划）。这也是"第一层必须存在"的根本原因：
域名判断只能交给能看到域名的那一层。

### 2.1 补强证据：整个 WFP 字段表里就没有"域名"这一个字段

上面那次实测只能证明"`ALE_EFFECTIVE_NAME` 不好使"，还证明不了"别的字段里
也没有"。所以把 `windows` crate 里 **全部** `FWPM_CONDITION_*` 常量（约 130 个）
列出来过一遍，跟"名字"沾边的只有四个：

| 字段 | 实际语义 | 能不能当域名用 |
|---|---|---|
| `ALE_EFFECTIVE_NAME` | 远端端点名（blob） | ⛔ 实测装得上拦不住（§2） |
| `PEER_NAME` | IPsec 对端名 | ⛔ 不是网站域名 |
| `IMAGE_NAME` | **本地**进程映像路径 | ⛔ 方向就反了 |
| `RPC_SERVER_NAME` | RPC 服务器名 | ⛔ 跟 HTTP 无关 |

**结论：WFP 的过滤条件里根本不存在"域名"这个原语。** 这不是"没找到合适的
写法"，是这一层压根没有这个维度。

## 2.2 那"屏蔽整个主域名"还能做到哪一步（已实测）

`examples/domain_probe` 把主域 + 常见子域解析成 IP 集合，逐个 IP 装持久化
阻断（`FWPM_FILTER_FLAG_PERSISTENT`，不设端口条件 = 整 IP 全断）：

```text
第一幕：域名 → IP（这一步是 DNS 干的，不是 WFP）
  baidu.com        → [110.242.74.102, 111.63.65.103, 111.63.65.247, 124.237.177.164]
  www.baidu.com    → [183.2.172.177]
  pan.baidu.com    → [36.110.192.103, 36.110.192.112]
  tieba.baidu.com  → [14.215.182.28]
  map.baidu.com    → [14.215.182.87, 14.215.182.217]
  image.baidu.com  → [14.215.182.180]
去重后共 11 个 IP → 已装 11 / 11 条

check（**另一个进程**）：6 个域名全部「断」
curl 实测：
  www.baidu.com     HTTP 000 (0.009s)
  pan.baidu.com     HTTP 000 (0.009s)   ← 子域也断了
  tieba.baidu.com   HTTP 000 (0.009s)
  map.baidu.com     HTTP 000 (0.009s)
  fanyi.baidu.com   HTTP 200 (0.396s)   ← ⚠ 没进列表的子域，照样通
```

⚠ **最后一行是这份实验真正的值钱之处。** 它证明这不是"按域名拦"，而是
"按此刻解析出来的 IP 拦"：

- `*.baidu.com` 是**无限集**，枚举法必然有漏；
- 同一个子域有多条 A 记录且会**随 TTL 轮换**，规则会过期；
- 多条 A 记录只命中一部分时，表现为"部分通"——最典型的快照漂移。

**要给用户的准确说法：WFP 这层能做到"把某个域名此刻的 IP 全断"，做不到
"这个主域名以后永远访问不了"。** 想要后者，只能在**解析环节**判后缀，
也就是 §5.5 的 DNS 漏斗。

## 3. 第二层的原语：`IP_LOCAL_INTERFACE`（已实测）

### 3.1 字段在不在：问引擎，不背文档

`examples/egress_probe` 用 `FwpmLayerGetByKey0` 枚举层字段
（"层支持哪些字段"会随版本 / SKU / 已装驱动变化，不能靠背）：

```text
ALE_AUTH_CONNECT_V4 —— 字段总数 41
  ✅ IP_LOCAL_INTERFACE   值类型 FWP_UINT64   ← 就是 NET_LUID
  ✅ INTERFACE_INDEX      值类型 FWP_UINT32
  ✅ IP_NEXTHOP_INTERFACE / NEXTHOP_INTERFACE_INDEX / TUNNEL_TYPE …
  ✅ 对照组 IP_REMOTE_ADDRESS / IP_REMOTE_PORT / ALE_APP_ID / FLAGS 全在
```

选 `IP_LOCAL_INTERFACE` 是因为 `aegis-sense` 产出的正是网卡 **LUID**
（`default_egress_luid`），两边是同一个标识，不需要再转换一次。

### 3.2 字段在 ≠ 分类时带着正确的值：必须做行为实验

ALE 是"连接授权"层，它发生在路由选择之前还是之后，决定了这个值有没有意义。
如果分类时它是 0，那"按网卡砍"就是一条**永不匹配的死规则**——装上不报错，
看起来在防，其实什么都没防。

`examples/iface_probe` 做三组，每组都装了立刻拆：

| 组 | 层 | 出口网卡条件值 | 实测 | 它在证明什么 |
|---|---|---|---|---|
| A | ALE_AUTH_CONNECT_V4 | **真实默认出口 LUID** | **断** | 值是对的，规则真的匹配这一跳 |
| B | ALE_AUTH_CONNECT_V4 | **假 LUID** | **通** | **阴性对照**：A 不是"匹配了一切" |
| C | OUTBOUND_TRANSPORT_V4 | 真实默认出口 LUID | **断** | 传输层也能钉住，可作兜底 |
| — | 收尾复核 | — | 通 | 规则都拆干净了 |

⚠ **B 组是整套实验的命门。** 没有它，A 的"断"可能只是"这条规则拦了
一切"——而"拦了一切"恰恰是我们要避免的假象：它看起来通过了，其实是拦错了范围。
（第一版脚本还因为把布尔量传反，把整张表打成了反的，差点得出相反结论。）

**结论：沙漏第二层的原语成立，且已经验证到"真的生效"这一层。**

## 4. 一个重要的补充：TUN 模式与系统代理模式要的原语**不同**

这一点原讨论里没区分清楚，但它直接决定规则怎么写。

| 模式 | 应用看到的连接 | 正确的放行原语 | 为什么 |
|---|---|---|---|
| **TUN 模式** | 应用 socket 仍连**真实远端 IP**，系统按路由把包送进 TUN | **按出口网卡**（走 TUN 放行 / 走物理卡阻断） | 若按"只放行代理进程"，应用自己的 socket 也会被拦掉，TUN 模式直接废掉 |
| **系统代理**（SOCKS/HTTP） | 应用连 `127.0.0.1:端口` | **按进程**（放行代理进程，其余全断） | 应用根本不直接连外网，按网卡判没有区分度 |

所以 Aegis 的计划不能写死一种，得按"当前代理工作模式"二选一。
这也正是 `aegis-wfp` 里 `Condition::EgressInterfaceLuid` 与
`Condition::SystemServiceHost`（AppId blob）并存的原因。

## 5. 还缺什么（要实现的清单）

原语有了，但**沙漏模型今天还没装上**。按依赖顺序：

### 5.1 配置面：把"该走哪张卡 / 谁是代理"变成显式配置

今天 `CagePolicy` 里没有这两项，规则只能写成"无条件"。要加：

| 待加字段 | 用途 | 来源 |
|---|---|---|
| `campus.luid` | 校园物理网卡（第二层要钉死的那张） | `aegis-sense` 拓扑裁决 |
| `proxy.mode` | `Tun` / `SystemProxy` | 适配器 SPI 从代理软件读 |
| `proxy.tun_luid` | TUN 虚拟网卡 LUID（`Tun` 模式） | 适配器 SPI |
| `proxy.image_path` | 代理进程映像路径（`SystemProxy` 模式） | 适配器 SPI |

⚠ **网卡 LUID 会变。** 禁用再启用网卡、重载驱动、USB 网卡重插，LUID 都可能变
（本项目已经踩过 RNDIS 幽灵网卡的坑）。所以：

- **不能**在配置文件里写死一个 LUID 就完事；
- 必须靠 `aegis-sense::delta` 的**拓扑差分**驱动规则重算——
  感知到物理网卡集合变了，就重算一遍第二层规则并原子替换。
- 重算失败时按 Fail-Closed 处理：**变成"全断"而不是"全放行"**。

### 5.2 规则计划：把"无条件默认拒绝"改成"走错网卡才拒绝"

当前十条里的第 5、8、9、10 条是**无条件阻断**——它们会把代理隧道一起砍掉，
所以现在的绝缘笼 = 整机断网（这是演练已验证的正确行为，但还不是沙漏）。

沙漏版应该是：

```text
放行  回环                              （保 GUI↔服务，最高权重）
放行  DHCP                              （保开机拿 IP）
放行  出口网卡 == TUN_LUID              ← 沙漏的核心放行（TUN 模式）
  或  进程 == 代理进程映像路径           ← 系统代理模式
阻断  出口网卡 == 校园物理网卡 LUID      ← 沙漏的核心阻断
阻断  目的端口 == 53 且 出口网卡 == 校园卡  （DNS 不得裸奔出校园卡）
阻断  OUTBOUND_TRANSPORT 层：出口网卡 == 校园卡   （覆盖存量连接）
```

⚠ 顺序（权重）仍然是安全承诺：放行必须严格高于阻断，否则放行规则会被
自己的阻断先吃掉——**静默失效，不报错**。这一点由 `aegis-wfp::verify` 的
不变量测试钉死。

### 5.3 适配器 SPI：读代理规则给 GUI

原讨论里"左边 Clash 规则、右边 Aegis 拦截状态"的设想是对的，
对应 `design-spec §2A` 已规划的**可插拔适配器**。要做的是：

- 从 Clash / sing-box 的 REST API 读当前生效规则与 TUN 网卡；
- 把它映射成 Aegis 这边的 `campus.luid` / `proxy.mode` / `proxy.tun_luid`；
- GUI 展示一张"流量在哪一层、哪个口被放行/拦截"的拓扑图。

### 5.4 兜底：ALE 层管不到的部分

- **ICMP**：ALE 层不管；要拦只能挂传输层（C 组实测 `OUTBOUND_TRANSPORT_V4`
  的 `IP_LOCAL_INTERFACE` 可用）。
- **已建立的存量连接**：同上，靠传输层那条兜底。
- **DNS 泄漏**：53 端口封锁已有，但要确认它绑在"校园网卡"上，
  而不是无条件——否则会误伤走 TUN 的 DoH/代理内 DNS。

### 5.5 域名级策略的唯一落点：DNS 漏斗（未实现，先论证）

§2.2 证明了 IP 枚举法覆盖不了"整个主域名"。唯一能精确按后缀判的地方，
是**域名被解析的那一刻**。可行的形态：

```text
应用 ──DNS 查询──▶ 127.0.0.1:53（Aegis 本地解析器）
                      │  按后缀判：*.baidu.com → NXDOMAIN / 127.0.0.1
                      └─▶ 放行：只有 Aegis 自己能对外发 53
WFP：阻断 53 出站（Aegis 解析器进程除外）  ← 强制所有查询都得过这道闸
```

为什么它比 IP 枚举强：

| | IP 枚举（§2.2） | DNS 漏斗 |
|---|---|---|
| `*.baidu.com` 无限集 | ⛔ 枚举不完 | ✅ 按后缀匹配，天然全覆盖 |
| IP 轮换 / TTL 过期 | ⛔ 规则会漂移 | ✅ 每次查询重判，不会过期 |
| CDN 共享 IP 误伤 | ⛔ 整 IP 全断会连坐 | ✅ 只挡"查这个域名"的动作 |
| fail-closed | ✅ 进程死了规则还在 | ✅ 进程死了 53 被堵 = 什么都解析不了 |

⚠ 代价与前提（别急着做）：

- 必须先把"53 出站只放行解析器进程"这条规则写对，写错就是**整机无法解析**，
  而此时 GUI 也连不上服务——和自锁死同一类事故；
- DoH（DNS-over-HTTPS）走 443，绕得过 53 封锁 → 需要配合"已知 DoH 服务器
  IP"或上层代理规则，不能指望 DNS 漏斗单独封死；
- 这是一个新组件（本地解析器），不是给 `aegis-wfp` 加个条件就行。

## 6. 对原讨论的两处修正

1. **"代理软件崩了，Aegis 在底层砍掉" —— 成立，但要说清用户体验。**
   代理崩了之后，应用流量会走默认路由从校园网卡出去 → 被砍 → **表现为断网**。
   这是期望行为（fail-closed，宁可断网也不带着校园网 IP 泄露），
   但必须让用户知道"代理挂了 = 断网"，而不是以为 Aegis 出了故障。

2. **"只要走错网卡就砍" —— 前提是规则绑在网卡上，不是无条件。**
   今天那十条里 4 条是无条件的，装上去是整机断网。沙漏版必须先把
   §5.2 的放行规则加进去，否则"漏斗"的下层是实心的，什么都过不去。

## 7. 复现命令

```bash
# 1. WFP 到底给不给"出口网卡"字段（只读枚举）
cargo run -p aegis-wfp --example egress_probe

# 2. 这个字段分类时带着正确的值吗（含阴性对照，会短暂拦百度 443）
cargo run -p aegis-wfp --example iface_probe

# 3. 域名能不能在 WFP 层拦（结论：不能）
cargo run -p aegis-wfp --example name_probe

# 4. 「整个主域名」能拦到哪一步（会装 11 条**持久化**规则，测完必须 purge）
cargo run -p aegis-wfp --example domain_probe -- arm
cargo run -p aegis-wfp --example domain_probe -- check   ← 另一个进程
cargo run -p aegis-wfp --example domain_probe -- purge   ← 必跑
```
