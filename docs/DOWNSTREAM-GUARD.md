# 下游规则失效时的兜底：Aegis 必须替它把门关上

> 需求原文：**"如果检测到规则未生效，需要帮下游软件兜底，全都拒绝掉。"**
>
> 本文只做两件事：(1) 说清**现状里已经有什么、缺的是什么**；
> (2) 把"什么叫规则生效"从一句口号变成**可判断言**。
>
> 结论先行：**兜底这一半早就写死在状态机里了（且有测试钉着），真正缺的是
> "检测" —— 而"规则未生效"比"代理挂了"难判得多，难在它大多是静默的。**

---

## 1. 先别急着写：兜底这件事，状态机早就保证了

`aegis-core::state` 里：

```rust
(State::Controlled, Event::ProxyUnhealthy) => State::Degraded,
```

而 `insulation()` 对 `Degraded` 的答案是 **`Full`**（完全绝缘 = 全部拒绝）：

```rust
State::Controlled    => Insulation::None,    // 唯一放行态
State::CaptivePortal => Insulation::CaptiveSandbox,
_                    => Insulation::Full,    // Degraded 落在这一支
```

并且 `insulation_is_pinned_per_state` 这条测试**逐状态钉死**了这张表——
谁把 `Degraded` 改成放行，测试立刻变红。

也就是说：**"下游不健康 → 全都拒绝"这条铁律已经是可执行的了**，
不需要新设计。真正的缺口在上一半：**`ProxyUnhealthy` 这个事件由谁、按什么判据产生。**

---

## 2. 核心难点：「规则生效」不是一个布尔量

现有事件的注释写的是"Clash/HypoMux **不可达**"。这**只覆盖了一种失效**，
而且是最容易发现的一种（进程没了 / 端口连不上）。

用户说的"规则未生效"是一类**完全不同、且更阴**的失效：

| 失效形态 | 进程在吗 | 端口通吗 | 规则生效吗 | 怎么被发现 |
|---|---|---|---|---|
| 代理进程崩了 | ❌ | ❌ | ❌ | 一眼可见 |
| 进程活着但 TUN 网卡没了 | ✅ | ✅ | ❌ | **静默** |
| TUN 在，但默认路由没指向它 | ✅ | ✅ | ❌ | **静默** |
| 系统代理模式下，系统代理开关被别的软件改掉了 | ✅ | ✅ | ❌ | **静默** |
| 配置加载失败，规则集为空（FINAL 走直连） | ✅ | ✅ | ❌ | **静默** |
| 规则在、但某个域名漏匹配 | ✅ | ✅ | 部分 | 几乎不可见 |

⚠ **这张表是这个需求真正的难点**：除了第一种，其余全部**不报错、不崩溃、
界面上看起来一切正常**，只是"该走的没走"。这正是本项目反复在抓的
**静默失败 / 假按钮**——兜底做得再狠，检测不到就等于没有。

---

## 3. 于是要定义四级断言（从弱到强）

"规则生效"必须拆成可分别验证的断言，而不是一个 `bool`。

| 级别 | 断言 | 判据 | 现在能不能做 |
|---|---|---|---|
| **A** | 代理还在 | 进程存在 / 控制端口可连 | ✅ 需要 SPI |
| **B** | 承载体还在 | TUN 网卡仍在拓扑中（拓扑差分） | ✅ **今天就能做**（`aegis-sense::delta`） |
| **C** | 路指向它 | 默认出口 == TUN 的 LUID | ✅ **今天就能做**（`aegis-sense::route::default_egress()`） |
| **D** | 端到端真的生效 | 对"必须被代理接管"的目的地做**路由试算**，看它走哪张卡 | 🟡 需要一个 canary 目的列表（配置） |

### 3.1 C 级断言说明（最值钱的一条）

`aegis-sense::route::default_egress()` 已经能给出"系统真正的默认出口"
（注意：用的是**合成度量**——接口度量 + 路由偏移，而不是裸读 `Metric`，
后者在自动度量下恒为 0，会把默认出口判错，这是踩过的坑）。

于是有一条**完全不需要 SPI、不需要外部网络**的判据：

```text
配置里写了 proxy.tun_luid = X
实际默认出口 LUID   = Y
X != Y  →  代理没有接管默认流量  →  规则未生效  →  兜底
```

它抓的就是表里第 3、4 行那两种静默失效。

### 3.2 D 级断言：用「路由试算」而不是「真的连一下」

最诱人的写法是"Aegis 自己连一个必须被拦的地址，看连不连得上"。
⚠ **别这么做**：

- 它依赖外网可达性 → 网络本来就抖动时会**误报**，而误报的代价是整机断网；
- 它会产生真实流量 → 审计日志被自己的探针污染；
- 探测本身会被规则影响，判不出"拦截"和"不通"的区别。

正确姿势是**问内核而不是发包**：对每个 canary 目的地调
`GetBestRoute2` 做路由试算，问"去这里会走哪张网卡"：

```text
canary 目的列表（配置：这些目的地必须被代理接管）
  对每个问 GetBestRoute2 → 出口网卡 LUID
  出现「走物理校园卡」 → 这一条漏了 → 规则未生效
```

它是**纯本地、无副作用、可在秒级反复跑**的，且不受外网状态影响。

⚠ 前提：canary 列表必须是"**必须走代理**"的目的地。
拿"按规则本就该直连"的地址去试算，会得出"走物理卡 = 正常"，
那判据就废了。这个列表只能来自代理规则 → 属于适配器 SPI 的活，
v0 可以先由用户在配置里显式给几个。

## 4. 兜底的**正确实现姿势**：撤掉放行，而不是新增拒绝

这一点必须写死，否则会造出第二个砖机风险。

绝缘笼的结构是：**默认拒绝是底板，放行是例外**。所以"全都拒绝"的正确做法是

> **把已装的放行规则撤掉**（放行本来就在动态会话里），
> 而不是去装一堆新的拒绝规则。

为什么必须这样：

| | 撤掉放行 | 新增拒绝规则 |
|---|---|---|
| 进程被杀 / 崩溃 | 会话没了 → 放行也没了 → **自动断**（天然 fail-closed） | 规则若持久化 → 断着救不回来 |
| 需要持久化吗 | **不需要**（动态会话即可） | 一旦持久化 = 误触发后重启都救不回来 |
| 误触发的代价 | 重启/重启服务即恢复 | 可能要手动清 BFE 存储 |
| 和现有机制 | 直接复用 `ApplyTicket::force_teardown` | 要新造一套 |

⚠ **兜底规则绝不能做成持久化。** `docs/PERSISTENT-CAGE.md` 的结论是
"底板可以持久化、放行保持动态"；而这里的兜底正是**把放行收走**，
所以它天然属于动态那一半。把它做成持久化，等于给误报装上了"重启无效"的后果。

## 5. 四个必须提前回答的陷阱

### 5.1 误报 = 整机断网，而断网时人最没辙

检测一抖就收紧，用户正在下载/开会就被掐断。必须防抖：

- 连续 **N 次**（建议 3）判定失败才收紧，单次失败只记录；
- 收紧后进入**冷却期**才允许自动放宽（防抖成"断—通—断"抽搐）；
- 每次收紧都写审计，且**带原因**（哪条断言失败）。

### 5.2 用户不知道为什么断 → 他会先把 Aegis 卸了

这是最现实的一条：代理自己出了 bug，Aegis 忠实地兜底成断网，
用户看到的是"Aegis 把我的网搞断了"→ 卸载 → **防护彻底归零**。

所以兜底**必须伴随可观测**：GUI 明确显示"因下游规则未生效（断言 C 失败：
默认出口不是 TUN），已收紧为全部拒绝"，并给出"查看代理状态 / 强制放行"入口。
这一点和 `docs/HOURGLASS.md` §6 的修正 1 是同一件事。

### 5.3 收紧自动，放宽要不要自动？

- **收紧必须自动**（否则兜底形同虚设）；
- **放宽建议自动但受控**：断言恢复且过了冷却期 → 自动放宽 + 记审计；
- 若同一小时内收紧超过 K 次 → 判定为"代理反复故障"，**停在收紧态等人工**，
  避免在故障的代理上来回开关。

### 5.4 「代理不可达」和「规则未生效」不能共用一个事件

两者恢复动作不同（前者等它起来，后者可能要人去改配置），
混在一个 `ProxyUnhealthy` 里，GUI 就说不清"到底为什么断"。
建议拆成两个事件，落到同一个 `Degraded` 状态——**状态不变，原因可辨**。

## 6. 最小实现路径

| 优先级 | 内容 | 落在哪 | 状态 |
|---|---|---|---|
| P0 | 拆出 `ProxyRulesIneffective` 事件（与 `ProxyUnhealthy` 并列，同样 → `Degraded`） | `aegis-core::state` | ✅ 已落地 |
| P0 | 断言 A/B/C 的裁决 + 防抖/冷却/反复故障 | `aegis-core::guard` | ✅ 已落地 |
| P1 | 配置面 `proxy.tun_luid` / `proxy.mode` / `always_allow` | `aegis-config` | ✅ 已落地（见 §7.1） |
| P1 | 断言 B/C 的**采集**：TUN 在不在 + 默认出口是不是它 | `aegis-core::guard::topology_inputs` | ✅ 已落地 |
| P1 | 编排器接线：定时采拓扑 → 判 → 喂 `GuardTracker` | `aegis-orchestrator` | ⬜ 待做 |
| P2 | 断言 D：路由试算 canary（`GetBestRoute2`） | `aegis-sense` + SPI | ⬜ SPI 未实现 |
| P2 | GUI 展示"为什么断" + 始终白名单管理 | Tauri | ⬜ |

### 6.1 已落地的部分长什么样

`aegis-core::guard`（纯逻辑，56 项单测里的 21 项归它）：

```rust
pub fn evaluate(facts: GuardFacts) -> GuardVerdict;   // 判"规则生效吗"
pub enum GuardVerdict { Effective, Ineffective { failed, reason }, Unknown { reason } }

pub struct GuardTracker;   // 带时间记忆
impl GuardTracker {
    pub fn observe(&mut self, v: &GuardVerdict, now_ms: u64, policy: GuardPolicy)
        -> GuardAction;    // Nothing / Tighten / Relax / NeedsHuman
}
```

三条被写成测试钉死的铁律：

| 铁律 | 测试 |
|---|---|
| **判不了 ≠ 通过**：没配 TUN LUID / 读不到默认出口 / 系统代理模式下没有可用断言 → `Unknown`，**不是** `Effective` | `a_missing_tun_config_is_unknown_not_effective` 等 4 条 |
| **单次失败不收紧**：连续 3 次才动作，中途成功清零 | `a_single_failure_does_not_tighten` / `one_success_resets_the_streak` |
| **收紧自动、放宽过冷却**：且 1 小时内自动收紧 3 次后转人工 | `the_cooldown_boundary_is_inclusive_of_the_deadline` / `flapping_beyond_the_limit_stops_and_asks_for_a_human` |

⚠ **`Unknown` 永远不改变状态**，这是刻意的：判不了的时候收紧，会变成
"SPI 还没实现 → 一进受控态就永久断网"。那不是 fail-closed，是**自锁死**。
`Unknown` 要当成已知的能力缺口去补（SPI），而不是当成"先断为敬"的理由。

### 6.2 采集：拓扑快照 → 事实

`aegis-core::guard::topology_inputs(&TopologySnapshot)` 取出
`(存在的网卡 LUID 列表, 默认出口 LUID)`，编排器的入口是：

```rust
let facts = cfg.guard_facts_from(&snap, proxy_reachable)?;   // None = 没配 mode
let verdict = aegis_core::guard::evaluate(facts);
match tracker.observe(&verdict, now_ms, GuardPolicy::default()) {
    GuardAction::Tighten(ev)  => /* 撤掉放行 → 全都拒绝 */,
    GuardAction::Relax(ev)    => /* 恢复按角色放行 */,
    GuardAction::NeedsHuman{r} => /* 停在收紧态，通知用户 */,
    GuardAction::Nothing      => {},
}
```

⚠ 两个"0 不是网卡"的坑（都已写进测试）：

- `TopologySnapshot::default_egress_luid` 用 **0 表示"没有默认路由"**，
  直接当 LUID 传会把"整机离线"误判成"出口是 LUID 0"；
- 配置里的 `tun_luid = 0` 同理，加载时**翻成 `None`**。否则守卫会拿 0 去
  跟真实默认出口比，永远不等 → 判定"未生效" → 持续收紧 → **永久断网**。
  （样例配置 `config.example.toml` 里写的就是 0。）

### 6.3 配置面（`aegis-config`，已落地）

```toml
[proxy]
mode     = "tun"          # tun | system_proxy，必填语义：不配 = 守卫不工作
tun_luid = 0x6008008000000000

[[always_allow]]          # 受控后门，见 §7.1
name      = "校园网认证页"
remote_ip = "10.254.1.1"
ports     = [80, 443]
```

`Config::guard_gap()` 用来回答"守卫现在能不能工作"，三种缺口如实报告：
未配 `mode` / TUN 模式缺 `tun_luid` / 系统代理模式等 SPI。
**缺配置不等于配置错**：前者照常加载 + 报告缺口，后者（例如白名单条目
`ports = []`）才按 Fail-Closed 拒绝加载。

## 7. 开放问题与已定的答案

### 7.1 ✅ 已定：「全都拒绝」与认证页的冲突 → 用**始终白名单**解决

> 用户决定：之后做 UI 时加一个"**始终白名单**"功能，用于放行校园网认证页。

这条解法是对的，但有个代价必须**先写出来**，否则做的时候会把它做成暗门：

> ⚠ **始终白名单必然破坏"只有走对网卡才放行"这条判据。**
> 校园网认证页只能从校园物理网卡访问 —— 而那正是平时要砍的那条路。
> 所以它不是"又一条放行规则"，而是一个**受控后门**。

于是实现时必须满足：

| 约束 | 理由 |
|---|---|
| **只能由用户显式添加**，任何自动流程 / SPI 都不许加 | 自动加 = 后门可被诱导打开 |
| **作用域钉到最小**：`目的 IP = 校园网关` + `端口 80/443`，不要写成"网关 IP 全端口" | 白名单越宽，沙漏下层的洞越大 |
| **权重必须高于所有阻断**，且纳入 `aegis-wfp::verify` 的不变量 | 权重写反 = 白名单静默失效（不报错，只是拦着） |
| **每次命中都写审计** | 后门必须可追溯，否则变暗门 |
| **兜底收紧时它仍然生效** | 这正是它存在的意义——否则用户永远出不来 |
| GUI 上标注为"永久放行"，并显示条目数 | 用户要能一眼看到自己开了几个洞 |

与认证沙盒的关系（两者并存，不冲突）：

| | 认证沙盒 `CaptivePortal` | 始终白名单 |
|---|---|---|
| 谁加的 | 系统自动（检测到未认证） | **用户手工** |
| 存续 | 临时，有租约超时 | 永久 |
| 范围 | 浏览器 → 网关 80/443 | 用户指定 |

配置面形态（`aegis-config`，待做）：

```yaml
always_allow:
  - name: 校园网认证页
    remote_ip: 10.0.0.1      # 校园网关
    ports: [80, 443]
```

### 7.2 仍然开放的三个问题

1. **阈值这组数**：N=3、冷却 30s、1 小时内 3 次转人工 —— 先用默认值跑，
   等真机用起来再调（已做成 `GuardPolicy`，改起来不用动逻辑）。
2. **canary 列表**由用户配，还是等 SPI 自动从代理规则里抽？
3. **要不要给用户一个"我知道风险，强制放行"的紧急出口**？
   （`EMERGENCY-TEARDOWN.md` 里已有强拆通道，可复用。）
