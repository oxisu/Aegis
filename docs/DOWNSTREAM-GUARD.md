# 下游规则失效时的兜底：Aegis 必须替它把门关上

> 需求原文：**"如果检测到规则未生效，需要帮下游软件兜底，全都拒绝掉。"**
>
> 本文只做两件事：(1) 说清**现状里已经有什么、缺的是什么**；
> (2) 把"什么叫规则生效"从一句口号变成**可判断言**。
>
> 结论先行：**兜底这一半早就写死在状态机里了（且有测试钉着），真正缺的是
> "检测" —— 而"规则未生效"比"代理挂了"难判得多，难在它大多是静默的。**

---

## 1. 先别急着写：兜底这件事，状态机早就保证了

`aegis-core::state` 里：

```rust
(State::Controlled, Event::ProxyUnhealthy) => State::Degraded,
```

而 `insulation()` 对 `Degraded` 的答案是 **`Full`**（完全绝缘 = 全部拒绝）：

```rust
State::Controlled    => Insulation::None,    // 唯一放行态
State::CaptivePortal => Insulation::CaptiveSandbox,
_                    => Insulation::Full,    // Degraded 落在这一支
```

并且 `insulation_is_pinned_per_state` 这条测试**逐状态钉死**了这张表——
谁把 `Degraded` 改成放行，测试立刻变红。

也就是说：**"下游不健康 → 全都拒绝"这条铁律已经是可执行的了**，
不需要新设计。真正的缺口在上一半：**`ProxyUnhealthy` 这个事件由谁、按什么判据产生。**

---

## 2. 核心难点：「规则生效」不是一个布尔量

现有事件的注释写的是"Clash/HypoMux **不可达**"。这**只覆盖了一种失效**，
而且是最容易发现的一种（进程没了 / 端口连不上）。

用户说的"规则未生效"是一类**完全不同、且更阴**的失效：

| 失效形态 | 进程在吗 | 端口通吗 | 规则生效吗 | 怎么被发现 |
|---|---|---|---|---|
| 代理进程崩了 | ❌ | ❌ | ❌ | 一眼可见 |
| 进程活着但 TUN 网卡没了 | ✅ | ✅ | ❌ | **静默** |
| TUN 在，但默认路由没指向它 | ✅ | ✅ | ❌ | **静默** |
| 系统代理模式下，系统代理开关被别的软件改掉了 | ✅ | ✅ | ❌ | **静默** |
| 配置加载失败，规则集为空（FINAL 走直连） | ✅ | ✅ | ❌ | **静默** |
| 规则在、但某个域名漏匹配 | ✅ | ✅ | 部分 | 几乎不可见 |

⚠ **这张表是这个需求真正的难点**：除了第一种，其余全部**不报错、不崩溃、
界面上看起来一切正常**，只是"该走的没走"。这正是本项目反复在抓的
**静默失败 / 假按钮**——兜底做得再狠，检测不到就等于没有。

---

## 3. 于是要定义四级断言（从弱到强）

"规则生效"必须拆成可分别验证的断言，而不是一个 `bool`。

| 级别 | 断言 | 判据 | 现在能不能做 |
|---|---|---|---|
| **A** | 代理还在 | 进程存在 / 控制端口可连 | ✅ 需要 SPI |
| **B** | 承载体还在 | TUN 网卡仍在拓扑中（拓扑差分） | ✅ **今天就能做**（`aegis-sense::delta`） |
| **C** | 路指向它 | 默认出口 == TUN 的 LUID | ✅ **今天就能做**（`aegis-sense::route::default_egress()`） |
| **D** | 端到端真的生效 | 对"必须被代理接管"的目的地做**路由试算**，看它走哪张卡 | 🟡 需要一个 canary 目的列表（配置） |

### 3.1 C 级断言说明（最值钱的一条）

`aegis-sense::route::default_egress()` 已经能给出"系统真正的默认出口"
（注意：用的是**合成度量**——接口度量 + 路由偏移，而不是裸读 `Metric`，
后者在自动度量下恒为 0，会把默认出口判错，这是踩过的坑）。

于是有一条**完全不需要 SPI、不需要外部网络**的判据：

```text
配置里写了 proxy.tun_luid = X
实际默认出口 LUID   = Y
X != Y  →  代理没有接管默认流量  →  规则未生效  →  兜底
```

它抓的就是表里第 3、4 行那两种静默失效。

### 3.2 D 级断言：用「路由试算」而不是「真的连一下」

最诱人的写法是"Aegis 自己连一个必须被拦的地址，看连不连得上"。
⚠ **别这么做**：

- 它依赖外网可达性 → 网络本来就抖动时会**误报**，而误报的代价是整机断网；
- 它会产生真实流量 → 审计日志被自己的探针污染；
- 探测本身会被规则影响，判不出"拦截"和"不通"的区别。

正确姿势是**问内核而不是发包**：对每个 canary 目的地调
`GetBestRoute2` 做路由试算，问"去这里会走哪张网卡"：

```text
canary 目的列表（配置：这些目的地必须被代理接管）
  对每个问 GetBestRoute2 → 出口网卡 LUID
  出现「走物理校园卡」 → 这一条漏了 → 规则未生效
```

它是**纯本地、无副作用、可在秒级反复跑**的，且不受外网状态影响。

⚠ 前提：canary 列表必须是"**必须走代理**"的目的地。
拿"按规则本就该直连"的地址去试算，会得出"走物理卡 = 正常"，
那判据就废了。这个列表只能来自代理规则 → 属于适配器 SPI 的活，
v0 可以先由用户在配置里显式给几个。

## 4. 兜底的**正确实现姿势**：撤掉放行，而不是新增拒绝

这一点必须写死，否则会造出第二个砖机风险。

绝缘笼的结构是：**默认拒绝是底板，放行是例外**。所以"全都拒绝"的正确做法是

> **把已装的放行规则撤掉**（放行本来就在动态会话里），
> 而不是去装一堆新的拒绝规则。

为什么必须这样：

| | 撤掉放行 | 新增拒绝规则 |
|---|---|---|
| 进程被杀 / 崩溃 | 会话没了 → 放行也没了 → **自动断**（天然 fail-closed） | 规则若持久化 → 断着救不回来 |
| 需要持久化吗 | **不需要**（动态会话即可） | 一旦持久化 = 误触发后重启都救不回来 |
| 误触发的代价 | 重启/重启服务即恢复 | 可能要手动清 BFE 存储 |
| 和现有机制 | 直接复用 `ApplyTicket::force_teardown` | 要新造一套 |

⚠ **兜底规则绝不能做成持久化。** `docs/PERSISTENT-CAGE.md` 的结论是
"底板可以持久化、放行保持动态"；而这里的兜底正是**把放行收走**，
所以它天然属于动态那一半。把它做成持久化，等于给误报装上了"重启无效"的后果。

## 5. 四个必须提前回答的陷阱

### 5.1 误报 = 整机断网，而断网时人最没辙

检测一抖就收紧，用户正在下载/开会就被掐断。必须防抖：

- 连续 **N 次**（建议 3）判定失败才收紧，单次失败只记录；
- 收紧后进入**冷却期**才允许自动放宽（防抖成"断—通—断"抽搐）；
- 每次收紧都写审计，且**带原因**（哪条断言失败）。

### 5.2 用户不知道为什么断 → 他会先把 Aegis 卸了

这是最现实的一条：代理自己出了 bug，Aegis 忠实地兜底成断网，
用户看到的是"Aegis 把我的网搞断了"→ 卸载 → **防护彻底归零**。

所以兜底**必须伴随可观测**：GUI 明确显示"因下游规则未生效（断言 C 失败：
默认出口不是 TUN），已收紧为全部拒绝"，并给出"查看代理状态 / 强制放行"入口。
这一点和 `docs/HOURGLASS.md` §6 的修正 1 是同一件事。

### 5.3 收紧自动，放宽要不要自动？

- **收紧必须自动**（否则兜底形同虚设）；
- **放宽建议自动但受控**：断言恢复且过了冷却期 → 自动放宽 + 记审计；
- 若同一小时内收紧超过 K 次 → 判定为"代理反复故障"，**停在收紧态等人工**，
  避免在故障的代理上来回开关。

### 5.4 「代理不可达」和「规则未生效」不能共用一个事件

两者恢复动作不同（前者等它起来，后者可能要人去改配置），
混在一个 `ProxyUnhealthy` 里，GUI 就说不清"到底为什么断"。
建议拆成两个事件，落到同一个 `Degraded` 状态——**状态不变，原因可辨**。

## 6. 最小实现路径

| 优先级 | 内容 | 落在哪 | 依赖 |
|---|---|---|---|
| P0 | 拆出 `ProxyRulesIneffective` 事件（与 `ProxyUnhealthy` 并列，同样 → `Degraded`） | `aegis-core::state` | 无（纯逻辑 + 单测） |
| P0 | 断言 B/C 的检测器：TUN 在不在 + 默认出口是不是它 | `aegis-sense` + `aegis-core` 裁决 | 已有能力 |
| P1 | 防抖 / 冷却 / 反复故障计数的纯逻辑 + 单测 | `aegis-core` | 无 |
| P1 | 配置面 `proxy.tun_luid` / `proxy.mode` / `guard.canaries` | `aegis-config` | HOURGLASS §5.1 |
| P2 | 断言 A/D：进程探测、路由试算 canary | `aegis-sense` + SPI | SPI 未实现 |
| P2 | GUI 展示"为什么断" | Tauri | — |

⚠ P0 的两条**不需要任何提权、不需要 SPI**，可以先做完并单测覆盖。

## 7. 需要用户拍板的开放问题

1. **兜底到什么粒度？**「全都拒绝」（本次需求）与「认证沙盒」
   （放行浏览器→校园网关 80/443，用来完成校园网认证）冲突吗？
   如果兜底时校园网还没认证，全拒绝会让用户**连认证页都打不开**。
2. **冷却期与阈值**：N=3、冷却 30s、1 小时内 3 次转人工 —— 这组数合适吗？
3. **canary 列表**由用户配，还是等 SPI 自动从代理规则里抽？
4. **要不要给用户一个"我知道风险，强制放行"的紧急出口**？
   （`EMERGENCY-TEARDOWN.md` 里已有强拆通道，要不要复用它。）
