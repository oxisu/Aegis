# 持久化绝缘笼：技术可行性与架构变更方案

> **状态：方案，未实施。** 本文只做评估与设计，不动代码。
> 落地前必须先跑完 §8 的验证实验清单。

---

## 0. 先把一句话说对

现在的动态会话（`FWPM_SESSION_FLAG_DYNAMIC`）防的是**"我们写错代码"**，
不是**"别人来杀我们"**。这两件事此前被混在一起讲了，是我的表述问题。

| 威胁 | 动态会话挡得住吗 |
|---|---|
| 我们自己写错一条规则、装出半套规则 | ✅ 挡得住（进程一退全清） |
| 代码 panic / 死锁 | ✅ 挡得住 |
| 蓝屏 / 断电 | ✅ 挡得住（内核内存没了） |
| **别人 `taskkill /F`** | ❌ **挡不住** |
| **恶意软件结束进程** | ❌ **挡不住** |

所以"防君子不防小人"这个批评**成立**。

### 0.1 但"死也不放开"的正确含义不是"杀不掉"

必须先打破一个幻想：**在本项目能拿到的权限范围内，进程防杀是做不到的**
（§3.C 有依据：真正的保护要 ELAM 驱动 + 微软签发的证书，开源项目拿不到）。

所以目标要换个说法，而这个说法才是真正可实现的：

> **不是"你杀不掉我"，而是"你杀了也没用"。**
>
> 无论用什么方式让 `aegisd` 停止存在——硬杀、撞崩、改配置、卸载——
> 结果都是**继续保持封锁**，而不是**网络自由**。
> 想恢复网络，必须走**正规的恢复动作**（本地、可审计、留下证据）。

这条才是"死了也不放开"。下面所有设计都围绕它。

## 1. 三个硬核维度，逐一评估可行性

微软官方文档 *Object Management*（WFP）给出了四种对象生存期，**这是本文全部设计的地基**：

| 生存期 | 何时消失 |
|---|---|
| **Dynamic** | 所属会话终止（= 进程死）或被删除 |
| Static | BFE 停止 / 系统关机 / 被删除 |
| **Persistent** | **被删除**（跨进程、跨重启都在） |
| Built-in | 永远 |

### A. 持久化规则（Persistent Filters）—— ✅ 可行，且不需驱动

- 做法：`FwpmFilterAdd0` 时给 `FWPM_FILTER_FLAG_PERSISTENT`，
  且**必须开一个非动态会话**（`FWPM_SESSION_FLAG_DYNAMIC` 会让对象根本进不了
  BFE 持久存储——动态会话不是"倾向临时"，而是**结构上禁止**持久化）。
- 生效时机：**"Persistent objects are added when BFE starts."**
  即 BFE 服务一起，规则就在。BFE 是 TCP/IP 栈的依赖，
  所以"网络一可用，笼子就已经在了"——对本项目够用。
- 落盘位置（Quarkslab 逆向 + 多篇运维案例一致）：
  `HKLM\SYSTEM\CurrentControlSet\Services\BFE\Parameters\Policy\Persistent`
  （Boot-Time 过滤器另在 `...\Policy\BootTime\Filters`）
  ⚠ **这条决定了离线逃生舱真实存在**：从 WinPE / 另一个系统挂载 SYSTEM hive，
  删掉这个键，规则就没了（§6 路径 3）。

### B. 服务化 + 失败自动重启 —— ✅ 可行，且不需驱动

- `SERVICE_FAILURE_ACTIONS` + `SC_ACTION_RESTART`：进程**未上报
  `SERVICE_STOPPED` 就终止**时，SCM 判定为失败并按配置重启。
- ⚠ **一个必须知道的关键差别**：
  - 任务管理器里"结束任务"→ 实际走的是 **SCM 停止服务** → **不触发**重启动作；
  - `taskkill /F` / `TerminateProcess`（恶意软件的做法）→ 不上报状态 → **触发**重启。
  - 所以"任务管理器关掉它"能成功，但**那之后规则仍在（持久化）**，网络照样是断的。
    自洽：想维护就走正规通道（`net stop` + `--purge`），想偷偷杀没用。
- `fFailureActionsOnNonCrashFailures = TRUE` 可把"退出码非 0"也算失败。
- **`SC_ACTION_RUN_COMMAND` 是救砖的关键**：第 N 次失败后可以执行一条命令。
  配成"连续失败 3 次 → 跑 `aegisctl --purge`"，
  就把"最坏情况有硬上界"这条纪律**在持久化时代保下来**（见 §5）。

### C. 进程防杀（PPL / 受保护服务 / 内核回调）—— ❌ 本项目拿不到

| 手段 | 门槛 |
|---|---|
| `SERVICE_LAUNCH_PROTECTED_ANTIMALWARE_LIGHT`（PPL 反恶意软件级） | 需 **ELAM 驱动** + 微软签发的**专用 Authenticode 证书**；厂商须向微软申请、签法律文件、过测试套件 |
| Protected Process Light（PPL） | 同上，需签名；连带 SeDebugPrivilege 的管理员也杀不掉 |
| `ObRegisterCallbacks`（内核回调拦 `TerminateProcess`） | **必须写驱动**，本项目明确定位为"不写驱动" |

**结论：不做。**
这条不是"以后再说"，是**结构性拿不到**。它反而说明 §0.1 那个目标转换是必需的：
既然挡不住"被杀"，就必须让"被杀"这件事**失去收益**。

**可做的降级项（提高成本，不是防住）：**
- 服务对象 DACL：`SetServiceObjectSecurity` 拒绝非 SYSTEM 的
  `SERVICE_STOP` / `SERVICE_CHANGE_CONFIG` / `DELETE`。
- 进程 DACL：拒绝非管理员 `PROCESS_TERMINATE`。
- ⚠ 诚实结论：**管理员（含 UAC 提权后）依然能赢**，可 `SeTakeOwnership`、
  可改服务配置、可挂注册表 hive、可用 WinPE。目标是提高成本和留下证据，不是防住。

### D. Provider 关联机制 —— ⚠ 意外挖到的"总开关"

微软文档里这条此前没人提，但它几乎是为本项目量身定做的：

> 添加 Provider 时可指定一个可选的 **Windows 服务名**；添加持久对象时可指定
> **拥有它的 Provider**。服务启动时，BFE **只在**以下情况才把持久对象加进系统：
> 该对象没有关联 Provider，**或**关联的 Provider 没有服务名，
> **或关联的服务被设为自动启动（auto-start）**。

也就是说：

```text
把持久化底板挂到 "provider = Aegis, serviceName = aegisd" 上
  ├─ aegisd 服务 = 自动启动  → BFE 加载底板 → 封锁生效
  └─ aegisd 服务 = 已禁用    → BFE 不加载底板 → 网络恢复（需重启）
```

这同时给了两样东西：

1. **自带的、文档化的逃生开关**（§6 路径 1）；
2. **卸载语义**：卸载 Aegis 时把服务禁用，重启后不留残党——
   不会出现"卸载了但网还是断"这种最招骂的事故。

⚠ 这条**必须在本机实测确认**（§8 第 2 项），因为它要重启验证，代价高，
不能只凭文档就写进代码。

## 2. 架构变更：底板持久化，放行靠活进程

这是整套方案的核心，一句话：

```text
底板（Persistent，无条件 Block）  ← 永远在，进程死了也在，重启也在
放行（Dynamic，走 aegisd 的会话） ← 只有 aegisd 活着时才存在
```

于是：

| 状态 | 底板 | 放行 | 结果 |
|---|---|---|---|
| 正常运行 | 在 | 在 | 按策略通行 |
| `aegisd` 被硬杀 | 在 | **没了** | **全断**（fail-closed） |
| 蓝屏 / 断电重启 | 在 | 没了 | **全断**，且开机即断 |
| 用户 `net stop` | 在 | 没了 | **全断**（要走恢复动作） |
| `--purge` | 删掉 | — | 网络恢复 |

### 2.1 为什么不放行也做成持久化

放行规则也必须**动态**。理由有三条：

1. 放行规则里含有**运行期才有的东西**（网卡 LUID、代理进程路径、TUN 网卡），
   持久化一个过期的 LUID 就是一条永不匹配的死规则——**放行失效 = 全断**，
   而全断你还不知道是为什么。
2. 微软明确：**持久对象不能引用动态/静态对象，也不能引用别的 Provider 拥有的
   持久对象**。把放行做成持久化，会把整个对象图绑死，逃生舱复杂度暴涨。
3. **"放行随进程消失"本身就是最可靠的心跳。** 不需要任何额外的心跳机制，
   不需要依赖"Provider 注销"这种未经本项目实测的语义（§2.2）。

### 2.2 关于原讨论里的"Provider 心跳"方案

原方案是：底板无条件持久化 + 放行绑 Provider，Provider 没了放行就没了。

**结论：方向对，但实现要简化。** 直接让放行规则跑在**动态会话**里，
效果完全一样（进程死 → 放行没），而且：

- 不依赖"BFE 是否会在 Provider 注销时删除过滤器"这个**有争议**的语义
  （微软文档说"必须先删除引用它的对象，才能删除该对象"，即**不级联**；
  而若干第三方代码注释称"删 Provider 会级联删除其下的过滤器"。两者矛盾，
  不能拿来做安全承诺）；
- 不需要额外的心跳/超时逻辑——进程存活性就是心跳，零延迟、零误判。

**逃生舱 `--purge` 因此也按文档化的顺序实现：先删 filter，再删 provider**，
绝不依赖级联。

### 2.3 持久化的**最小集**原则

只把这两条持久化：

```text
1. 默认拒绝（ALE_AUTH_CONNECT_V4/V6，无条件 Block）
2. 53 端口封锁（绑校园网卡）
```

其余全部动态。持久化面越小，逃生越简单，变砖概率越低。
**DHCP 放行必须动态**——它是"开机拿 IP"的保命规则，
做成持久化等于把一个可能过期的东西焊死在系统里。

## 3. 状态机变更

现有 §26 已有 `Bricked → Recovery`（地雷二），本次在此基础上增补：

```text
                ┌──────────────────────────────────────┐
                │  Boot（开机，持久化底板已由 BFE 加载） │
                └──────────────────┬───────────────────┘
                                   │ aegisd 服务启动
                      ┌────────────▼────────────┐
                      │ 上次有"优雅告别标记"？   │
                      └────────┬─────────┬──────┘
                          有   │         │ 没有（非正常终止 / 首次）
                               ▼         ▼
                        ┌──────────┐  ┌──────────────┐
                        │ Controlled│  │ Armed（待解除）│
                        │ 装动态放行 │  │ **保持封锁**   │
                        └──────────┘  └──────┬───────┘
                                             │ 恢复动作（§4）
                                             ▼
                                       Controlled
```

- **`Armed` 是新增的关键态**：它意味着"笼子锁着，但没有放行规则"，
  即**整机断网**。系统停在这里等人，不会自己放行。
- 判据用**自有的"优雅告别标记"**，不用读 `Minidump` / 事件 6008：
  自己的标记是自己写的、语义明确、可验证；OS 的崩溃日志是**佐证**不是**判据**。

## 4. 恢复仪式（Dead Man's Switch）

进入 `Armed` 后，解除封锁需要一次**显式的、本地的、留下证据**的动作。
三选一，都不需要网络：

| 方式 | 谁用 | 需要什么 |
|---|---|---|
| `aegisctl --restore` | 命令行用户 | 提权 + token |
| GUI 输入恢复码 | 普通用户 | 安装时生成的离线恢复码（用户自存） |
| 安全模式 `--purge` | 出事时 | 见 §6 路径 2 |

**超时行为：默认继续封锁，不是自动解除。** ⚠ 这一条要能配置——
无人值守的机器（服务器/实验室主机）可能希望"超时自动恢复"，
但默认值必须是 fail-closed，且切换时要显式警告。

⚠ 恢复动作本身必须**写进审计链**：`Armed → Controlled` 是谁、什么时候、
用什么方式解的，是事后复盘的关键证据。否则"谁把笼子开了"说不清。

## 5. 把"最坏情况有硬上界"这条纪律保下来

今天演练脚本（§`tools/cage-drill.sh`）的第二层兜底是
**`--serve-secs 45` 硬上界**：脚本被杀、终端被关都无所谓，45 秒后一定恢复。

持久化之后，这个上界**失效了**（规则不随进程消失）。必须换成：

```text
SCM 失败动作（SERVICE_FAILURE_ACTIONS）
  第 1 次失败 → 立即重启
  第 2 次失败 → 60 秒后重启
  第 3 次失败 → SC_ACTION_RUN_COMMAND：aegisctl --purge   ← 自动救砖
```

⚠ `aegisctl --purge` **绝不能加载配置文件**。配置错误正是启动失败的主因之一；
一个"因为配置错了才需要跑、跑了又因为要读配置而失败"的救砖命令是废物。
`--purge` 只做一件事：连 BFE、删掉 Provider 名下的所有对象、退出。

## 6. 逃生舱（Break-Glass），按"依赖越少越靠前"排序

| # | 路径 | 需要 aegisd 活着？ | 需要网络？ | 代价 |
|---|---|---|---|---|
| 0 | `aegisctl --purge`（提权，直连 BFE） | ❌ 不需要 | ❌ | 无 |
| 1 | 把 `aegisd` 服务设为**禁用** → 重启（§1.D 的 Provider 开关） | ❌ | ❌ | 一次重启 |
| 2 | **安全模式**下手动起服务或跑 `--purge` | ❌ | ❌ | 一次重启 |
| 3 | **离线**：WinPE / 挂盘，加载 SYSTEM hive，删 `...\BFE\Parameters\Policy\Persistent` | ❌ | ❌ | 需介质 |
| 4 | 系统还原 / 重装 | ❌ | ❌ | 最大 |

⚠ 路径 3 是真正的最后兜底，它存在的前提是 §1.A 那条注册表位置**在本机被确认**。
这条必须实测（§8 第 4 项），否则手册里写一条可能不成立的方法，比不写更糟。

⚠ 安全模式下 BFE 仍会运行（它是基础服务），第三方持久化过滤器**很可能照样加载**
——所以路径 2 成功与否取决于"能否在安全模式下启动 aegisd 或跑 --purge"，
而不是"安全模式会不会绕过过滤器"。这条也要实测（§8 第 6 项）。

## 7. 变砖风险矩阵（持久化带来的新增风险）

| 新增风险 | 概率 | 后果 | 对策 |
|---|---|---|---|
| 持久化底板 + aegisd 起不来 | 中 | **永久断网** | SCM 第 3 次失败自动 `--purge`（§5） |
| 放行规则引用了过期的网卡 LUID | 中 | 放行失效 = 全断 | 放行**永不持久化**（§2.1） |
| 配置损坏导致启动失败 | 中 | 同上 | `--purge` 不加载配置（§5） |
| 删除 provider 没删干净 | 低 | 残党导致持续断网 | 按 filter → provider 顺序删，删除后**枚举复核** |
| 卸载后仍留持久规则 | 低 | 卸载了网还是断 | Provider 服务名开关（§1.D） |

**核心对策只有一条：任何新增的持久化，都必须配一条"不需要 aegisd、不需要网络、
不需要配置"的删除路径，并且这条路径要先于持久化功能被测试。**

## 8. 落地前必跑的验证实验（未完成前不写产品代码）

| # | 要验证什么 | 方法 | 代价 |
|---|---|---|---|
| 1 | 本机能否在非动态会话里装 `FWPM_FILTER_FLAG_PERSISTENT` 规则 | 新探针（`Session::open_persistent`） | 低，需提权 |
| 2 | **Provider + serviceName 开关是否真的生效** | 装持久规则 → 禁用服务 → 重启 → 查是否还拦 | **要重启** |
| 3 | 删 provider 是否级联删 filter（预期：**不**级联） | 先试删 provider，看返回值与残留 | 低 |
| 4 | 持久对象在本机注册表的实际位置与形态 | 装一条 → 查 `...\BFE\Parameters\Policy\Persistent` | 低 |
| 5 | SCM 失败动作能否在 `taskkill /F` 后拉起服务；`RUN_COMMAND` 是否触发 | 装成服务实测 | 中 |
| 6 | 安全模式下 BFE 是否仍加载第三方持久过滤器；能否手动起 aegisd | 进安全模式实测 | **要重启** |
| 7 | `--purge` 能否在无 aegisd、无配置、无网络的情况下清干净 | 端到端 | 低 |

⚠ 2 和 6 要重启，属于"长任务 + 有干扰"。按约定，**跑之前先问你要不要跑**，
且要挑你不在用网的时段。

## 9. 明确不做的事

| 不做 | 理由 |
|---|---|
| **Boot-Time 过滤器**（`FWPM_FILTER_FLAG_BOOTTIME`） | 唯一能在 TCP/IP 栈启动前生效的手段，代价是**装错即变砖**；而 BFE 起来后 Persistent 就接管了，收益极小。现有 `preflight` 拒绝 `Tier::Boot` 的约束**继续保留** |
| 写驱动（含 `ObRegisterCallbacks`） | 项目定位就是不写驱动；且驱动本身的稳定性风险 >> 收益 |
| 追求 PPL / 受保护服务 | 需要 ELAM + 微软签发证书，开源项目结构性拿不到（§1.C） |
| 放行规则持久化 | 见 §2.1 |
| 用读 minidump 作为非正常终止的判据 | 只作佐证；判据用自有的优雅告别标记（§3） |

## 11. 一句话总结

**动态会话解决的是"我们别把自己锁死"，持久化解决的是"别人别把锁打开"。
两者不是替代关系，是分层：**

```text
放行规则（动态）  → 保证我们写错了不会把用户锁死
```
