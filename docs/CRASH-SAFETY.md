# 崩溃安全：断电 / 蓝屏 / 强杀之后，会留下什么

> 本文回答的具体问题是：
> **"联通时主机断电、未联通时主机断电、系统蓝屏，重启完之后会不会因为
> 数据损坏而无法联网 / 一直断网 / 或者出现别的怪事？"**

---

## 0. 一句话结论

**不会。重启之后一定是干净的，且一定能联网。**

理由只有一条，但它足够：

> Aegis 装的 WFP 规则全部活在**动态会话**（`FWPM_SESSION_FLAG_DYNAMIC`）里，
> 而动态会话里的对象**只存在于内核内存**，从不写入 BFE 的持久存储。
> 进程没了 → 没了；内核没了（断电 / 蓝屏重启）→ 更没了。

也就是说**清理不靠我们的代码执行**。这一点是刻意设计的：崩溃路径上
根本没有机会执行清理代码，所以"记得在退出前清理"从一开始就不算兜底。

---

## 1. 五种异常场景，逐条说清

| # | 场景 | 当时笼子在不在 | 重启后留下什么 | 能不能联网 | 依据 |
|---|---|---|---|---|---|
| A | **装着笼子时断电** | 在 | 什么都没有（规则随内核内存消失） | ✅ 正常 | 实测（见 §2） |
| B | **没装笼子时断电** | 不在 | 只有 token 文件 + 审计日志 | ✅ 正常 | 实测（见 §3） |
| C | **蓝屏** | 任意 | 同 A/B，且更彻底 | ✅ 正常 | 由 A 外推（见 §4） |
| D | **重启后数据损坏导致无法联网** | — | **不存在这条路径**（我们不写任何影响联网的持久状态） | ✅ | 代码级证据（见 §5） |
| E | **BFE 服务起不来** | — | 一条规则都装不上 | ✅ 通（但**没有绝缘**） | 见 §6 |

⚠ 注意 E 的危险方向：BFE 挂掉的后果是**没有防护**（fail-open），
不是**断网**。这与角色裁决的 Fail-Closed 是两件事，别混为一谈。

---

## 2. 场景 A 的实测：进程被硬杀之后规则还在不在

正常退出验了不算数——它证明的是"我们的 `rollback` 写得对"，不是
"崩溃路径安全"。要验的是**清理代码一行都没跑**的那条路径。

所以有了 `tools/crash-drill.sh`：

1. 装一条**只拦 `www.baidu.com:443`** 的规则（不装整副笼子：
   整副笼子的 blast radius 是整机断网，万一验证不成立就只剩重启能救；
   只拦一个 IP 验证的是同一件事，最坏情况只是百度暂时打不开）；
2. 进程装完之后**挂住不动**，不拆、不 `drop`、没有 `Drop` impl；
3. `taskkill /F`（= `TerminateProcess`：没有 atexit、没有 DLL 分离、
   没有析构）—— **在进程侧这就是断电 / 蓝屏的等价形态**；
4. 再测连通性。

本机实测结果（`2026-10-18`）：

```text
装之前 通
装之后 断                                    ← 规则确实生效（否则"消失"毫无意义）
BFE 里叫「崩溃探针」的过滤器 = 1              ← **阳性对照**：装着时查得到
taskkill /F 之后 通                          ← 进程没了，内核把规则清了
BFE 里叫「崩溃探针」的过滤器 = 0              ← 连 BFE 里也没有残留
```

**兜底在内核侧，不在我们的代码里。** 这正是断电 / 蓝屏要的保证。

### 2.1 一个差点被放过的假测量

第一版脚本里那条"netsh 里残留 = 0 条"是**空的**：`netsh wfp show filters`
**不往 stdout 输出**，它在**当前目录**写一个 `filters.xml`（本机 2.9 MB）。
于是 `netsh ... | grep -c` 恒为 0 —— 看起来通过了，其实什么都没测。

现在加了**阳性对照**：装着的那一刻必须先查得到（实测 1 条），强杀之后才
谈得上"查不到"。没有阳性对照的"0"不是证据，只是没测到。

## 3. 场景 B：没装笼子时断电

不涉及任何内核对象。落在盘上的只有两个文件，都不影响联网：

| 文件 | 断电时的形态 | 重启后 |
|---|---|---|
| `.aegis-run/ipc.token` | 写了一半 / 旧内容 | 每次启动 `CREATE_ALWAYS` 覆盖，旧 token 当场失效 |
| `.aegis-run/audit-*.binlog` | 末尾可能躺着一条只写了一半的记录 | 自愈（见 §7） |

---

## 4. 场景 C：蓝屏 → 为什么可以从 §2 外推

蓝屏与"进程被强杀"的差别在于：蓝屏时**内核也停了**。而我们的规则
活在内核内存里，所以只会更干净，不会更脏。

⚠ 蓝屏真正的额外风险在**文件**而不是网络：正在写的文件可能损坏。
我们只写两个文件（见 §3 表），且两者都有明确的复位语义。
本版**不写**注册表、不注册服务、不装驱动、不改网卡配置、不改路由表。

> 断电 / 蓝屏本身**不在这台机器上实测**——不该为了验证而故意弄崩一台
> 正在用的机器。所以 §4 是**推断**，不是实测。实测的是 §2。
> 两者的差距只有"内核有没有正常走完关机流程"，而这条差距只会让结果更安全。

## 5. 场景 D：为什么不存在"数据损坏导致无法联网"

要造成"重启后无法联网"，必须往**影响联网的持久状态**里写过东西。
Aegis 一处都没有。可复核：

```bash
# 是否写注册表 / 注册服务 / 装驱动
grep -rn "RegSetValue\|RegCreateKey\|CreateService\|OpenSCManager\|ChangeServiceConfig" crates/ --include=*.rs
# → 0 处
```

以及四条代码级硬约束：

1. **不装 Boot 层规则**。`aegis-wfp::preflight` 见到计划里有
   `Tier::Boot` 就直接拒绝下发（`RefuseReason::BootRulesPresent`）。
   Boot 层对象是唯一能跨重启存活的 WFP 对象——**它从源头就被禁掉了**。
2. **不设 `FWPM_FILTER_FLAG_PERSISTENT`**。代码里出现这个常量只是在
   **识别别人装**的持久过滤器，从不用于我们自己的下发。
3. **不改网卡 / 路由 / DNS**。感知层 `aegis-sense` 全程只读。
4. **不改用户的配置文件**。配置加载器不使用默认值、也不回写。

于是"重启后因为 Aegis 的数据损坏而连不上网"这条路径**在结构上不存在**。

## 6. 场景 E：BFE 服务起不来会怎样

`FwpmEngineOpen0` 依赖 Base Filtering Engine（BFE）。BFE 挂了：

- `aegisctl apply` 失败 → **一条规则都装不上** → 网络**通**；
- 代价是**没有绝缘**，也就是 fail-open。

方向要认清楚：这是"防护缺席"，不是"断网"。
反过来，如果笼子已经装着而 BFE 被停掉，BFE 会带走它名下所有过滤器
（含动态会话里的），笼子同样消失。

> BFE 在 Windows 上是受保护服务，正常手段停不掉。这里说的是"它自己
> 起不来"这种故障态，不是有人去停它。

## 7. 顺带修掉的两个真洞（都是**实测**发现的）

崩溃安全这一轮不是只写文档，它真的抓出两个洞，都已修掉并加了回归测试。

### 洞 1：一次掉电会让守护进程**永久**起不来

`aegisd` 原来用 `AuditLog::create`（`create_new`，拒绝覆盖）。于是一次
掉电留下的日志文件，会让**之后每一次**启动都失败：

```text
[FATAL] 无法创建审计日志：文件存在。 (os error 80)
=== 退出码：5 ===
```

也就是说"一次断电把服务永久打趴在地上"——这正好是崩溃安全的反面。

修法：`AuditLog::open_or_create`——存在就**续写**（保住证据），不存在才新建；
并把这次做了什么如实打印出来：

```text
打开方式  : 新建
打开方式  : 续写（已有 3 条）
打开方式  : **修复**：末尾 166 字节残记录已截断丢弃，保留 3 条完整记录
```

连续三次重启（`.aegis-run` 一个文件都不删）实测：退出码 0，链连续。

### 洞 2：写到一半的审计记录会被判成"证据被篡改"

掉电时最后一条记录只写了一半，这是**正常工况**，不是有人动手脚。
原来的读取逻辑把它一律判成 `ReadError::Corrupt`，于是 `open` 失败 →
守护进程又起不来。

修法：严格区分**掉电**与**篡改**。只有这两种**可证明的不完整**形态
才被当成掉电丢弃：

- 长度前缀本身没写全（不足 4 字节）；
- 前缀写全了，但声明长度超过文件里实际剩下的字节。

除此之外一律照旧报 `Corrupt`：内容哈希对不上、序号跳号、前驱不连续、
声明长度小到连链节都放不下——这些只可能是改动。并且加了
`MAX_RECORD_LEN`（1 MiB）上限：把长度前缀改成一个离谱的大数不会被当成
掉电静默吞掉。

残记录还会**真的从文件里截断**，不只是"读的时候跳过"。留着它，下一条会
接在残记录后面，文件中间就出现一段谁也解析不了的字节——下次重开会把它
判成篡改，而它其实只是上次掉电的遗物。

端到端实测（把真实 binlog 尾部砍掉 30 字节）：

```text
切断前：819 字节 → 切断后：789 字节
打开方式  : **修复**：末尾 166 字节残记录已截断丢弃，保留 3 条完整记录
回读校验  : OK（4 条，链完整）
修复后文件大小：819
```

## 8. 诚实说明代价：掉电会丢最后几条审计记录

`AuditLog::append` 之后 `flush` 只保证进了 OS，**不保证落盘**；
要保证落盘得调 `sync`。

默认策略是**定期 sync 而不是每条 sync**——每条都 sync 会把 WFP 事件速率
直接压到磁盘速率上。代价就是：**掉电可能丢最后几条记录**。

这不是缺陷，是取舍；但必须说清楚，不能让"我们已经落盘了"变成一个
未经说明的假设。已落盘的部分仍然完整可校验——链不断。`sync` 的节奏策略
属于待定项，正式版要按事件速率定一个明确的秒数并写进配置。

另外一条老实话：哈希链能检测**改动**，检测不了**尾部整段删掉**
（删掉之后末尾那条的前驱自然就成了新的链头，链条仍然自洽）。
这是哈希链的结构性限制，不是实现问题。见 `crates/aegis-audit/src/chain.rs`
的模块文档。

## 9. 真出问题时的恢复顺序

崩溃场景下其实**不需要恢复**（重启就是干净的）。如果观察到异常，
按 `docs/EMERGENCY-TEARDOWN.md` 的顺序走：

```text
第 0 层  10 秒倒计时        aegisd 自己撤
第 1 层  aegisctl rollback  本地 IPC 强拆（断网也能用：NPFS 不经 IP 栈）
第 2 层  结束 aegisd 进程   动态会话随之清空
第 3 层  重启               本版不装 Boot 层规则，重启一定干净
```
